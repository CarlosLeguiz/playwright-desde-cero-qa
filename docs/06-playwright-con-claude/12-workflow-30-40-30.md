# 12. El workflow 30 / 40 / 30

## Que es

Es una regla para repartir el esfuerzo cuando automatizas tests con IA. Dice que el trabajo se divide asi:

- **30% pensar** (antes de escribir nada)
- **40% generar** (la IA escribe el codigo)
- **30% validar y endurecer** (vos revisas y mejoras)

El error tipico del QA que recien arranca con IA es saltarse el primer 30% y el ultimo 30%. Pide "genera un test de login", acepta lo que salga, y despues se pregunta por que la suite es inestable.

---

## El primer 30%: pensar

Antes de abrir Claude Code, definis:

**Que vas a testear**
- Cual es el flujo critico? (el que si se rompe, pierde plata la empresa)
- Que casos: happy path, error, borde?

**Con que datos**
- Usuarios de prueba, credenciales, datos de entrada
- Que datos son fijos y cuales cambian

**Que significa "paso"**
- Cual es la assertion que realmente prueba que funciono
- No alcanza con "el boton se clickeo"; tiene que verificar el resultado

**Que locators tiene el sitio**
- Tiene `data-testid`? Tiene labels? Es React con clases generadas?
- Esto lo descubris con DevTools (Inspect > Copy outerHTML)

Si no haces este paso, la IA va a adivinar. Y adivina mal.

---

## El 40%: generar

Aca entra Claude Code. Le pasas lo que pensaste en el paso anterior:

```
Genera un test de Playwright en TypeScript para el flujo de checkout
de https://www.saucedemo.com

Contexto: usuario standard_user / secret_sauce, ya probado que el login funciona

Flujo:
1. Login
2. Agregar "Sauce Labs Backpack" al carrito
3. Ir al carrito
4. Checkout con nombre "Carlos", apellido "Leguizamon", zip "5000"
5. Confirmar

HTML de los elementos clave:
(pegar outerHTML)

Verificaciones:
- El badge del carrito muestra "1"
- El total incluye el precio del producto + impuesto
- Al final aparece "Thank you for your order!"

El sitio usa data-test como atributo. Configura testIdAttribute en el config.
```

Este paso es rapido. La IA escribe en segundos lo que a mano te llevaria 20 minutos.

**Nota:** si estas usando MCP, la IA puede navegar el sitio ella misma y sacar los locators reales. Eso reemplaza la parte de pegar outerHTML.

---

## El ultimo 30%: validar y endurecer

Este es el paso que separa un test que sirve de uno que te va a dar dolores de cabeza.

### Validar

1. **Corre el test**: `npx playwright test archivo.spec.ts --headed`
2. **Miralo correr**: el browser hace lo que esperabas?
3. **Rompelo a proposito**: cambia un dato para que falle. Falla? Si pasa igual, la assertion no sirve.

Un test que nunca puede fallar no es un test.

### Endurecer

Preguntas que te tenes que hacer sobre el codigo generado:

**Los locators son estables?**
- Si usa `.css-1x7hj2k` o `div > div > span:nth-child(3)`, cambialo
- Prioridad: `getByRole` > `getByLabel` > `getByTestId` > CSS

**Hay esperas fijas?**
- Si ves `waitForTimeout(3000)`, reemplazalo por una assertion web-first

**Las assertions prueban algo real?**
- `toBeVisible()` sobre el boton que acabas de clickear no prueba nada
- Tiene que verificar el resultado del flujo

**El test es independiente?**
- Puede correr solo, sin depender de que otro test haya corrido antes?
- Deja el sistema como lo encontro?

**Maneja el sitio lento?**
- Si es un sitio externo inestable, necesita `retries` o un timeout mayor

## Ejemplo del ciclo completo

**Pensar (30%)**

"Quiero verificar que el filtro de precio ordena bien. Datos: la lista de 6 productos de saucedemo. Paso = los precios quedan en orden ascendente. El select tiene `data-test="product-sort-container"`."

**Generar (40%)**

```
Genera un test que seleccione "Price (low to high)" en el dropdown de
ordenamiento de saucedemo y verifique que los precios quedan ordenados
de menor a mayor.

El select tiene data-test="product-sort-container" con option value="lohi".
Los precios estan en .inventory_item_price con formato "$29.99".

Lee todos los precios, convertilos a numero y verifica que el array
esta ordenado ascendente.
```

**Validar y endurecer (30%)**

Corre. Pasa. Ahora:
- Lo rompo: cambio "lohi" por "hilo". Falla? Si. Bien, la assertion sirve.
- Los locators: usa `getByTestId`, bien.
- Hay waits fijos? No.
- Es independiente? Si, hace login al principio.

Listo. Test confiable.

---

## Por que importa el reparto

| Si te saltas... | Que pasa |
|-----------------|----------|
| El primer 30% (pensar) | La IA adivina locators y datos. Test fragil o directamente mal. |
| El 40% (generar) | Escribis todo a mano. Funciona pero tardas 10x mas. |
| El ultimo 30% (validar) | Tenes tests que pasan siempre, incluso cuando la app esta rota. Peor que no tener tests. |

El valor de la IA no es que te saca el trabajo de encima. Es que te saca el trabajo **mecanico** (tipear codigo) para que uses tu cabeza en lo que importa: decidir que testear y verificar que el test sirva.

---

## La parte que sigue siendo tuya

La IA no sabe:
- Cual es el flujo critico de tu negocio
- Que bug se repitio tres veces el mes pasado
- Que el cliente usa siempre Firefox
- Que ese campo acepta decimales pero el backend los redondea

Eso lo sabes vos. La IA escribe el codigo; la estrategia de testing sigue siendo del QA.
